# 渐进式 ESM 迁移方案

> **已归档，未排期。** 本方案不执行。`apps/desktop/app/` 下没有任何 import：
> 零个 `import ... from`，零个 `type="module"`；而 CLAUDE.md 的「不要引入」
> 清单明确排除「前端框架，或给 app JS 加转译/构建步骤——它按设计就是纯拼接的
> JS」，而本方案正需要那一步。保留它是为了其中的推理，不是当作待办。
> 归档于 2026-08-22。

这是后续方案，不属于安全、额度、持久化或渲染修复的一部分，也不授权迁移框架或重做 UI。

## 目标

- 先把低耦合浏览器逻辑改为明确 import，再处理有状态功能。
- 逐步减少共享顶层全局命名空间。
- 保留现有 HTML、窗口结构、主题、产品文案和公开 API。
- 全程保持现有生成 bundle、打包应用、离线启动和公开快照流程可用。

## 兼容桥

每项迁移能力只保留一份 ESM 实现。仅在旧调用者仍需要时，增加一层薄桥，继续暴露现有
`window.AISystem6*` 契约。兼容桥只能转发调用，不能保存第二份实现，也不能重复执行初始化。
新的 ESM 代码直接 import 模块，不得反向依赖兼容全局。

在最终启动阶段之前，runtime manifest 仍是加载顺序的唯一来源。构建工具必须拒绝模块与
兼容桥的重复所有权，也必须拒绝底层 export 已不存在的兼容桥。

## 顺序

1. **清点与门禁**
   - 生成顶层声明、懒加载器、内联 handler 与 `window.AISystem6*` 契约的依赖图。
   - 搬迁前先增加启动顺序、离线加载、兼容桥身份与公开快照完整性测试。

2. **纯逻辑模块**
   - 从不访问 DOM、IndexedDB、storage、网络或可变全局的确定性 helper 开始：解析、
     规范化、校验、hash、token 估算与模型路由策略。
   - 每个提交只移动一个所有权簇，并保留原有测试。

3. **只读 registry 与数据 adapter**
   - 通过明确 export 迁移应用 registry、翻译/数据 reader 与不可变配置。
   - 保持当前懒加载边界；不能为了简化 import 把重型数据塞进启动路径。

4. **状态服务**
   - 持久化、写租约与 store facade 只有在 transaction 和 fence 已有黑盒覆盖后才能迁移。
   - 注入 storage、clock、channel 与 database 依赖，不得把它们藏进新的模块级 singleton。

5. **功能模块**
   - 每次转换一个应用，从叶子模块向共享 coordinator 推进。只有所有 ESM 调用者不再读取
     其兼容全局时，该功能才算迁移完成。
   - 保持应用懒加载、取消、错误码与用户可见行为。

6. **启动迁移与兼容桥退场**
   - 只有全部启动关键依赖都已模块化，且 bundle 大小/启动门禁仍在预算内，才能引入 ESM
     启动入口。
   - 删除最后一个全局调用者时，在同一提交删除对应兼容桥。
   - 只有 Chromium、WebKit、打包应用、离线与干净公开快照门禁都不再依赖拼接 bundle，
     才能退役拼接流程。

## 提交与验证规则

- ESM 搬迁不得混入行为改变、样式、重命名或数据迁移。
- 每个提交必须可独立回退；有旧调用者时通过兼容桥维持原公开 API。
- 每个阶段边界都运行 build、功能契约、checkJs、服务端 typecheck、Chromium/WebKit smoke
  和干净公开快照 smoke。
- 把顶层全局与兼容桥 export 数量作为只降不升的指标；增加时必须明确说明兼容原因。

## 完成标准

浏览器源码具有明确依赖边、ESM 与全局之间没有重复实现、所有兼容桥均已删除或被记录为公开
兼容 API，且现有产品和发布门禁保持通过，迁移才算完成。React、Svelte 或其他 UI 框架不在
本方案范围内。
